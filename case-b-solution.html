案例 B：从一页纸到 Demo

走查 S1 的决策清单、FR、对象模型、生命周期、界面与仍待确认的边界。

本页要回答一个切片如何落成可演示、可写回的方案，哪些地方仍是假设？

读完你能

  • 把 CB-04 的六段转成 CB-07 的五条 FR；
  • 解释 Allocation 的状态迁移与写回；
  • 列出至少三条仍待确认的事项。

前置

先读：把决策写成一句可验收的 FR、方案设计四件套

这一页只做走查：S1 怎样从一页纸走到可演示、可写回的方案，哪些地方仍是假设。读之前你应当看过 FR 固定句和方案设计四件套；遇到不熟的词，先回去补。

案例已匿名化（场景见[S19]），数字都是【示例】，不是真实医院结论。

起点：一页纸到底定死了什么

案例 CB-04 是 S1 的范围契约。它用六段把“做什么、不做什么”压在一页里：

一页纸的段 本案写了什么 在方案里落到哪
用户 陈静操作；赵岚确认；周主任审批 决策人、界面权限
决策 本月各亚专科用多少额度、分给谁 唯一最终决策
输入 需求、额度、可用天数、资质、结转规则 对象属性与增强
动作 调整、看冲突、写回、提交确认与审批 生命周期与写回
价值 分配从约 3 小时降到 1 小时以内【示例】 后续 KPI
不做什么 不做个人排班、住院总轮转、工资绩效 Demo 边界

成功标准很硬：陈静能用真实一个月的数据完成一次分配；C1、C2 被识别并至少解决一个；周主任能在界面上完成审批；结果写回后可重开核对。

一页纸不是需求文档，是范围契约；哪一段没有产物接住，哪里就会在第五天变成“这个也要做”。

决策清单：一句最终决策，拆成四行

一页纸只有一句最终决策：本月每个亚专科用多少额度、分给谁。但操作时，陈静要连续做几个中间决定。决策清单（A04-01）就是把这些决定一行一行摆出来。

编号 决策 决策人 时点 输入 动作 频率 影响对象
DC-1 各亚专科本月额度怎么分 周主任（陈静提方案） 每月 25 日前 需求、额度、可用天数、资质 确认或调整分配方案 每月 三个亚专科的额度与人员分配
DC-2 某个人分到哪个亚专科 陈静 分配时 人员可用天数、资质、组长偏好 把人拖入亚专科并保存 每月多次 人员与亚专科的分配记录
DC-3 出现缺口时怎么办 陈静 + 赵岚 发现冲突时 缺口大小、可借额度、内部人手 借调、改派或申请额外额度 每月 1–3 次 缺口涉及的亚专科与人员
DC-4 最终方案是否发布 周主任 每月 27 日 阻断性冲突是否清零、缺口是否有负责人、总额度是否超 审批并写回 每月 月度分配方案与额度状态

编号用 DC（Decision），与 Day1 工具包的 D1（第一天）区分。DC-1 和 DC-2 是同一业务动作的两面，合并成 one-pager 的一个最终决策；DC-3 是缺口出现后才触发的中间决策；DC-4 是审批动作。赵岚的组长确认是 DC-4 之前的子步骤，不单独占一行。清单写多了，常见原因不是范围变大，而是把“查看”“导出”这类动作误写成决策。

五条 FR：哪些已经能验收

案例 CB-07 把上面的决定写成了五条 FR。下面补上可观察的验收点，数字仍用案例固定值【示例】。

FR 谁、在哪、做什么 验收时看什么 依赖的数据
FR-01 查看额度全景 陈静按月查看各亚专科需求、额度、已分配、剩余、缺口 Demo 三个亚专科逐行可见；真实科室 12 个只作背景；缺口非零时显示差额 月份、额度、已用、需求
FR-02 分配人员 陈静把人员拖入亚专科，填人天并保存；校验可用天数与资质 王芳可用 9 天，填 10 天时被阻止并提示超出 1 天 人员、可用天数、资质
FR-03 识别并解释冲突 冲突面板显示类型、对象、差额和建议动作 C1 显示超排 1 天；C2 显示缺口 2 人天 冲突类型、差额、对象
FR-04 组长确认 赵岚看到本组分配，选择确认或调整，意见写回记录 确认后状态变化；意见重开仍在 确认人、意见、状态
FR-05 主任审批与写回 周主任看冲突与总额度，批准后写回 分配为已发布；额度已用与剩余同步变化；重开仍在 审批人、状态、已用、剩余

FR-03 容易被写歪：系统只负责把差额和后果摆出来，先解决哪个、怎么调仍由陈静决定。FR-05 则相反，批准后必须写回，否则审批只是一次点击。

FR-02 的“资质校验”还带着假设：资质由谁认定，目前没有定论。黄金样例按目标态写“阻止保存”；口径确认前，Demo 降级为“高亮提示 + 组长确认”，并登记在待确认清单里。

对象模型：Allocation 连接人与亚专科

案例 CB-05 的对象模型有七个对象，与演示最相关的是五个：

对象 类型 关键属性 关系
人员 Person core 姓名、岗位、资质、可上班型、可用天数 属于多个亚专科；有多条分配
亚专科 Subspecialty core 名称、负责人、月度需求 有多个额度与分配
额度 Quota core 月份、额度人天、已用、剩余 属于亚专科；驱动分配
分配 Allocation use case 月份、人员、亚专科、人天、状态 连接人员与亚专科
冲突 Conflict derived 类型、对象、差额、严重度 指向分配或额度

基数决定校验怎么写：一个人员可分配到多个亚专科（1:N）；一个亚专科有多条分配（1:N）；一条分配只属于一个人员和一个亚专科。

对象模型不是数据库表。 冲突是算出来的，可以没有“冲突表”；分配由用户在界面创建，源系统里可能只有排班结果，没有“分配方案”。

用 FR 反查：FR-02 需要人员、亚专科、分配和额度；FR-03 需要冲突；FR-05 需要分配状态和额度已用。指不到对象的 FR，要么漏了对象，要么写虚了。

生命周期与写回：批准以后发生什么

案例 CB-06 给了 Allocation 的状态链：

建议 → 已确认 → 已发布 → 调整中 → 已归档
当前状态 Action 迁移后 写回字段 谁可操作
建议 确认分配 已确认 状态、确认人 陈静
已确认 发布 已发布 状态、发布时间 周主任
已发布 发起调整 调整中 状态、调整原因 陈静
调整中 重新发布 已发布 状态、新版本号 周主任
已发布 归档 已归档 状态、归档时间 系统/陈静

额度 Quota 的链路是：草稿 → 待确认 → 已确认 → 执行中 → 已关闭。两条链在“发布”处交汇：分配发布时，额度的已用增加、剩余减少。

演示时，周主任点“批准”，必须同时发生三件事：分配状态变为“已发布”；额度已用与剩余数字变化；关掉重开后两者都还在。少一件，都只能叫“界面演示”，不能叫“决策落成数据”。

写回还要有权限和失败处理：陈静可以确认，但不能替周主任发布。审批要区分两类冲突：阻断性冲突（如 C1 超排）未清零时，批准按钮禁用；结构性缺口（如 C2）允许带缺口批准，但每条缺口必须有负责人和日期。权限没谈下来就先写本地对象，并标明风险。

界面与 Demo：一条路径走完

S1 的界面只承载四个意图：看全景、做分配、处理冲突、完成审批。连起来就是 Demo 主线：

  1. 陈静打开额度全景：妇科 10、乳腺 22、消化 22 人天；妇科需求 12，C2 显示缺口 2 人天。
  2. 她在分配台把王芳拖入某个亚专科，填 10 天；王芳可用 9 天，保存被阻止，C1 提示超出 1 天。
  3. 她改成 9 天，冲突面板只剩 C2；她申请额外 1 天额度，缺口从 2 降到 1，剩余 1 天登记负责人和日期。
  4. 赵岚在组长确认页确认并留下意见；周主任看到“阻断性冲突已清零、剩余缺口有负责人”，在审批页批准，返回列表后分配为已发布、额度已变，刷新后仍在。

这条路径走通，方案才算支撑决策。Demo Readiness 检查的不是“页面做完没有”，而是路径有没有真实证据：

  • 用真实月份的脱敏数据，不是手搓的玩具数据；
  • 陈静本人操作，不由 FDE 代点；
  • 从看到缺口到审批写回全程走通，写回后重开仍在；
  • 数据或权限出问题时，有离线快照或降级路径，不假装成功；
  • 需要签字的审批人在场，或明确改成“先操作、次日补审批”。

任一项没证据，结论只能是“有条件 Go”或“不 Go”，不能写成“已就绪”。

停一下：把检查项套到你的项目上：哪一项有证据？只有口头保证的那项，就是演示前最大的风险。

哪些已经固定，哪些仍是假设

先把话说清：本案例是教学样例。下面说的“已固定”，只表示它在当前案例设定里被一页纸、访谈或规则库写死，不等于真实医院已经确认，更不能拿去当客户事实。

已经在案例设定里固定的（仍全是【示例】）：最终决策与“不做什么”（CB-04）；五条 FR 的角色、界面、动作（CB-07）；对象及三类划分（CB-05）；两条状态链（CB-06）；额度 10/22/22（妇科/乳腺/消化）、C1 超 1 天、C2 缺口 2 人天。它们分别支撑范围、验收、对象、写回与演示断言。

仍然待确认的，集中在一张清单里（案例 CB-11）：

待确认问题 影响什么 当前假设 演示时的处理
额度能否跨月结转 缺口计算 不能结转 按不能结转演示并注明
外部人员资质谁认定 FR-02 校验强度 由组长认定 只提示、不阻断
临时调整是否同审批链 Allocation 状态 走简化审批 本期不演示
写回院内系统权限 真实写回 先写本地对象 明确不是院内系统
基线 3 小时是否准确 价值声明 回忆值，偏高 先计时，不承诺降幅

这张表是方案的一部分：藏起来会被一句“谁说的”击穿，摆出来反而更容易拿到确认。

坑 1：把【示例】数字当成客户事实。 表现：汇报时说“你们现在要 3 小时，我们能降到 1 小时”。后果：基线只是回忆值，实测不符就伤信任。 处理：数字标【示例】；先测基线，测不了就只描述行为变化。

坑 2：把待确认规则写成系统能力。 表现：FR 写“自动认定资质”，Demo 也演成自动通过。后果：追问口径时无法回答。 处理：按当前字段校验，口径未定只提示，并放回待确认清单。

坑 3：Demo 只演界面，不演写回。 表现：点批准弹“成功”，不展示状态和额度变化。后果：无法证明决策落成数据。 处理：每次演示都留一个“关掉重开”的动作。

坑 4：让 FDE 代操作。 表现：演示时全是实施人员在点。后果：采用信号是假的。 处理：让陈静本人操作，FDE 只准备数据和兜底。

三问自测

1. CB-04 的六个段落，分别由哪些方案产物接住？ 用户与决策落到决策清单和权限；输入落到对象属性与增强；动作落到生命周期与写回；价值落到后续 KPI；不做什么落到 Demo 边界。
2. Allocation 从“已确认”到“已发布”，写回了什么？为什么这一步是 Demo 的关键？ 写回状态与发布时间，同时额度已用增加、剩余减少。它把审批从界面动作变成数据变化，关掉重开仍可见，才能证明决策落成数据。
3. 举出本案至少三条仍待确认的事项，并说明演示时怎么处理。 额度是否跨月结转（按不能结转演示）；资质由谁认定（只提示不阻断）；临时调整是否同审批链（本期不演示）；写回院内系统权限（先写本地对象）；基线 3 小时是否准确（先计时）。任答三条即可。

本章带走

  1. 一页纸每段都要有产物接住；最终决策只有一个，其余是中间决策，不是新范围。
  2. 五条 FR 能验收，靠角色、界面、动作和可观察结果；写回让审批落成数据。
  3. 方案里必须同时有“已固定”和“待确认”两张清单；【示例】数字不是客户事实，未确认规则不能伪装成系统能力。
