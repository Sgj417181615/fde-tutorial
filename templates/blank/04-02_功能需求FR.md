# A04-02 功能需求FR

> 产物路径：`04_方案设计/04-02_功能需求FR.md` ｜ 所属阶段：04_方案设计 ｜ 阶段门：G4

## 用途

把决策清单落成可验收的功能需求（FR，Functional Requirement），确保每条需求都能回答：谁、在哪个界面、看什么输入、做什么决定、执行什么动作、怎样算通过。

## 何时用

- 决策清单确认之后、画原型或写代码之前；
- 与业务方逐条确认“这个屏幕到底帮你做什么决定”时；
- Demo 前逐条验收，确认每条 FR 都能被真实用户走通；
- 发现页面越画越多时，回到这里删掉没有决策支撑的需求。

## 填写说明

1. FR 编号唯一，建议用 `FR-01`、`FR-02`，并与决策清单中的决策对应。
2. 用户写角色，不写“用户”两个字；界面写具体屏幕或区块名称。
3. 输入写字段或数据项，不写“相关数据”。
4. 决策写这一步要做的判断；一条 FR 只承载一个决策。
5. 动作动词开头，写用户实际点击、拖拽、填写或确认的操作。
6. 验收标准必须可观察、可复现，不写“体验良好”“响应迅速”。
7. 证据 ID 对应证据台账；推断或待验证的证据要保留状态，不能写成事实。
8. 写完后用四个红旗信号自查：说不清谁在什么界面做什么决定、一条 FR 塞了两个以上决策、只有“体验良好”、需要的数据现场拿不到却写成必须。

## 质量门自检（G4）

- [ ] 每条 FR 有唯一编号，并能追溯到决策清单中的某个决策。
- [ ] 写明用户与界面，能回答“谁在哪个屏幕做什么决定”。
- [ ] 一条 FR 只承载一个决策，没有把查看、分配、审批混在一起。
- [ ] 输入字段在对象模型或数据清单中有来源。
- [ ] 动作是用户动作，不是“系统应该支持”这类无法验收的表述。
- [ ] 验收标准可观察、可复现，没有“体验良好”一类空话。
- [ ] 关键 FR 有证据 ID；推断类证据没有伪装成事实。
- [ ] 四个红旗信号已逐条自查。
