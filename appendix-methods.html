方法库

按阶段、产物、角色、成熟度、证据等级、场景自动索引十张方法卡。

本页要回答哪个方法能解决我眼前这个具体问题？

读完你能

  • 按维度筛出相关方法卡；
  • 判断方法卡的证据等级与成熟度；
  • 知道新增方法卡要改哪些文件。

前置

无前置，从本页开始。

你手里有一个很具体的问题：“这条规则到底能不能配置？”或者“Demo 前我还差什么？”这时你不需要再读一遍主线，而需要一张能直接照着做的小卡。

方法卡是一张回答一个可操作问题的小卡：有明确的输入、步骤、输出、检查清单和反模式。它不是章节缩写，也不重新解释概念；概念仍归主线或工作台页，卡片只负责“这种情况怎么做”。

方法库由这些卡组成，按阶段、artifact、角色、成熟度、证据等级和场景索引。下面先是十张卡的总表，再给五张筛选表。每张卡都可以单独打开，三到五分钟读完。

三步找到该用的卡

  1. 先按阶段缩小：你现在在 00 项目章程还是 05 五天验证？阶段错了，方法再对也用不上。
  2. 再按 artifact 或角色缩小：你手里要产出哪个文件、你以什么角色参与？两个条件通常能筛到一到两张。
  3. 最后核对成熟度与证据等级：这张卡是在真实交付里验证过，还是只在试点或概念阶段？证据来自官方、第三方还是实践？

成熟度和证据等级是两件事。一张卡可以“已验证”，但证据等级仍是“实践”——它在一两次交付里奏效，不等于有官方背书。反过来，官方来源的方法也可能还没在你的场景里验证过。

停一下：你现在的问题，能不能写成“我要产出哪个 artifact，遇到什么判断困难”？如果写不出 artifact，先回到工作台页确认当前步骤，不要用方法卡代替问题定义。

新增第 11 张卡

新增方法卡不改导航：左栏的“方法库”分组和页面顺序由构建器按 _content/methods/ 目录扫描生成，不需要改 nav.json，也不需要手工注册页面。你要做的是：

  1. 在 _content/methods/ 新建 mc-11.md，写全 front matter（id、type、title、question、stage、artifacts、roles、scenarios、maturity、evidence_level、owner、uses、inputs、outputs、steps、checklist、anti_patterns、related、source、license、sources、word_budget）。
  2. 确认 owner 指向已存在的页面，且该概念已在 owners.json 登记；卡片只能用 uses，不能自己拥有概念。
  3. 确认 artifacts 里的 ID 都已在 artifacts.toml 注册；新 artifact 要先注册并补模板。
  4. 确认 related 里的页面、方法卡或 artifact 都能解析。
  5. 运行构建与检查；构建器会生成 methods/mc-11.html、写入搜索索引，并自动收进下面的“构建器自动索引”。
  6. 上方“十张卡总表”和各筛选表是人工编排的推荐路径，可按需补一行；即使不补，新卡也不会失踪。

构建器自动索引

这张表直接读方法卡的 front matter，每次构建重新生成。新增、改名或调整阶段/角色/成熟度后，不需要手改本页；它是方法库的兜底索引，上方人工表负责推荐，这张表负责不漏。

读法建议

不要从 MC-01 顺序读到 MC-10。方法库是查用库，不是教程。第一次接触，建议按“证据 → 追问 → 切片 → 规则 → 打分”读 MC-06、MC-07、MC-02、MC-01、MC-05，先建立从现场到切片的链路；准备评审时再读 MC-03、MC-04；启动和演示前读 MC-08、MC-09；项目结束读 MC-10。

本章带走

  1. 方法卡一张只回答一个可操作问题，用“阶段 → artifact/角色 → 成熟度/证据”三步筛，不要顺序通读。
  2. 成熟度与证据等级要分开看：已验证不等于官方，实践证据也不等于不能再用。
  3. 新增第 11 张卡不用改导航；补 front matter、确认 owner/artifact/related 合法，自动索引会收录它。
