方案设计四件套

对象模型、生命周期、数据增强、界面意图：让方案真的支撑那个决策。

本页要回答怎样的方案设计才算“支撑决策”，而不是堆页面？

读完你能

  • 区分 core、derived、use case 三类对象；
  • 画出带 Action 与写回的状态迁移；
  • 判断一个增强该放数据层还是应用层。

前置

先读：把决策写成一句可验收的 FR

演示前一天，你把页面排得很整齐：左边人员池，中间亚专科卡片，右边一个“确认分配”按钮。点下去，弹出一句“操作成功”。

周主任问：“批完以后，剩余额度变了吗？”你切回列表，数字没动；再刷新，状态还是“建议”。

问题不在页面，而在页面背后没有对象、没有状态、没有写回。这一页讲 Solution Design（方案设计）：把 FR 变成四件互相咬合的产物——对象模型、生命周期与写回、数据增强、界面意图。做完，你得到 A04-01 决策清单模板、A04-03 对象模型模板、A04-04 生命周期与写回模板、A04-05 增强与界面模板。

方案设计到底在回答什么

方案设计不是“画几张页面”，也不是“先选一个低代码工具”。它按顺序回答四个问题：

问题 产物
这个世界有哪些东西，它们怎么相连？ Object Model（对象模型）
东西有哪些状态，谁通过什么动作改变它？ Lifecycle Diagram（生命周期图） 与写回
为了做这个决定，还缺哪些信息？ Enrichment（数据增强）
用户要完成什么意图，需要怎样的交互？ Interface Expectation（界面意图）

顺序不能倒：先想界面，会得到一堆“看起来像”的页面；先想对象和状态，界面才有东西可放。官方把 solution design 作为从需求走向实现的独立阶段【官方】[S03]，并强调按可验证的增量排序【官方】[S04]；四件套是本项目的实践拆法【实践】[S17]。

对象模型：描述业务，不是建表

对象模型用对象、关系和基数，描述这个 use case 里“世界由什么组成”，先于数据库，也独立于具体工具。

先给名词和动词建模

画实体之前，先把客户嘴里的词对齐。同一家公司里，“客户”“账户”“计费实体”“org_id”常指不同边界的东西：销售说的是关系，财务说的是谁付款，开发只看见一个编号。两个部门都说“活跃客户”，分母和时间窗也可能不同。【第三方】[S15]

先定两件事。名词的边界：一个词在这个 use case 里指谁，和相邻的词差在哪。动词：决定、分配、审批、写回、撤销，每个动词对应一种状态变化和一个权限。名词决定对象，动词决定 Action。

一个检查：同一个词在同一张图上出现两次，含义是否相同？不同，就拆成两个对象或两个关系。不拆，后面的校验和指标一定打架。

三类对象：core、derived、use case

把对象分成三类，判断会简单很多：

  • Core 对象：源系统里直接有、粒度对得上。例如人员、亚专科、班型、额度。
  • Derived 对象：源系统没有，需要算出来或人工维护。例如冲突、缺口、剩余额度。
  • Use Case 对象：用户在流程中会主动创建、修改。例如分配、调整记录。

案例 CB-05 给出了 S1 的对象模型，压缩后是这样：

对象 类型 关键属性 关系 来源
人员 Person core 姓名、岗位、资质、可上班型、可用天数 属于多个亚专科；有多条分配 人事 + 排班本
亚专科 Subspecialty core 名称、负责人、月度需求 有多个额度与分配 科室配置
额度 Quota core 月份、亚专科、额度人天、已用、剩余 属于亚专科；驱动分配 人力资源
分配 Allocation use case 月份、人员、亚专科、人天、状态 连接人员与亚专科 用户在界面创建
冲突 Conflict derived 类型、对象、差额、严重度 指向分配或额度 规则计算

关系基数决定校验怎么写：人员和亚专科是多对多（N:N），由“分配”连接，所以一条分配只对应一个人员和一个亚专科（两侧 N:1）；一个冲突指向一条分配或一个额度。基数写错，校验和统计都会错：把多对多写成 1:N，系统会允许一个人重复算进同一亚专科，缺口永远算不平。

对象模型不是数据库表

对象模型不是数据库表。 数据库表回答“数据怎么存”，对象模型回答“业务里有什么、它们怎么关联、能对它做什么”。

差别有三条：一个对象可能落在多张表里（人员的资质、可用天数来自不同地方，业务上仍是一个人）；派生对象可能没有表（冲突是算出来的，可以是视图，不需要“冲突表”）；use case 对象常常在源系统里不存在（分配由用户创建，源系统只有“排班结果”）。

对象还带动作：表只有行列，对象有状态和可执行动作。所以先对象模型、再决定存储；反过来先建表，容易把业务关系压扁成外键。

画完用三条检查：每条 FR 能否指到对象和动作？每个对象是否有来源和负责人？派生对象能否说清从哪些字段、按哪条规则算出来？

Ontology（本体） 落到这个 use case，就是把对象、关系和可执行动作显式写出来，让它像一套 API 一样被界面和规则调用。

生命周期与写回：决策有没有落成数据

对象有了，接着问：它会经历哪些状态？谁通过什么动作推动它？动作之后，哪些字段真的变了？

案例 CB-06 给了两个状态机。先看分配 Allocation：

建议 → 已确认 → 已发布 → 调整中 → 已归档
当前状态 Action 迁移后 写回字段 谁可操作
建议 确认分配 已确认 状态、确认人 陈静
已确认 发布 已发布 状态、发布时间 周主任
已发布 发起调整 调整中 状态、调整原因 陈静
调整中 重新发布 已发布 状态、新版本号 周主任
已发布 归档 已归档 状态、归档时间 系统/陈静

额度 Quota 则是：草稿 → 待确认 → 已确认 → 执行中 → 已关闭。分配“发布”时，额度的已用与剩余要跟着变。

额度这条链同样要写清 Action、写回和权限，否则它会变成“另一个对象的待办”：

当前状态 Action 迁移后 写回字段 谁可操作
草稿 提交确认 待确认 状态、提交时间 陈静
待确认 确认 已确认 状态、确认人、确认时间 周主任
已确认 开始执行 执行中 状态、执行月份 陈静
执行中 关闭 已关闭 状态、关闭时间 周主任

两条链在“发布”处交汇：Allocation 发布让 Quota 已用增加、剩余减少；Quota 关闭后不再接受新分配，历史分配仍可查。“分配发布”不改变 Quota 状态，只更新数字，是跨对象联动，不是一次迁移。演示时只改了状态、数字没动，就是两条链没接上。

写回是方案的一部分。 它不是开发阶段“顺手补一下”的功能，而是方案是否成立的分界线。写回 的定义很朴素：用户动作真的修改了对象数据，而不只是切换页面或弹提示。

判断有没有写回，看三个现象：动作后对象状态在列表里变了；相关数字变了（已用增加、剩余减少）；关掉重开，变化还在。少一条，审批就只是表演，Demo 时一刷新就穿帮。

写回还要配三样东西：权限（陈静能确认，只有周主任能发布）、校验（超过可用天数阻止保存并说明差额）、回退（调整中可重新发布，已归档不可直接改）。

不要把状态机和泳道图混用。状态机 看一个对象的状态与 Action；泳道图看多个角色在时间上的交接。一个回答“数据怎么变”，一个回答“人怎么协作”，不能互相代替。

一个检验：画不出状态迁移，说明这个决策还没有落成数据。 如果 FR 说“陈静决定分给谁”，对象却没有“建议/已确认/已发布”这些状态，这个决定就只存在于她脑子里。

停一下：挑一条你写的 FR，问：它改变了哪个对象的哪个状态？如果答案是“没有状态，只是保存了一下”，要么补状态，要么承认它只是一个辅助动作。

记录系统的权威是制度性的

写回哪里？先给 写回 找落点：不是“哪个库方便”，而是记录系统——组织里被制度承认的那套记录。月结信哪套余额，审计认哪套日志，离职从哪里收权，三件事指向的系统就是它。

这不是技术偏好。换掉记录系统，等于换掉审计链和责任链。新工具该接在它上面：读它的数据，往它写回，继承它的权限、校验和审计，而不是在旁边另起一套“更好用”的表。旁边那套一旦成了第二个真相，就是一本平行账：两边对不上时没人知道该信谁，最后仍要有人手工同步。

三个问题判断有没有接对：

  • 哪个系统是权威？说不出来，就是还没找到写回目标。
  • 写回哪个字段？只写进自己的表，审批仍是表演。
  • 出现第二个真相时谁停？没有停用规则，平行账会一直长。

数据增强：缺的信息从哪来

用户做决定时，原始字段往往不够。额度表只有“额度人天”和“已用”，陈静真正要看的是“还剩多少、缺口多大、冲突在哪”。这些补充概念就是 Enrichment（数据增强）。

判断放哪层只有一句：不依赖用户手工修改、能由数据确定的，放数据层；需要人判断、批注或临场决定的，放应用层。

增强项 输入 计算或来源 放哪层
剩余额度 额度人天、已用 额度减已用 数据层
缺口 需求、已分配 需求减已分配，负数记缺口 数据层
冲突 C1 可用天数、分配人天 分配超过可用天数即超排 数据层
建议动作 冲突类型、差额 规则给候选，陈静决定 应用层
资质认定口径 当前资质字段 口径未定，不能自动判定 先提示，后确认

数据层稳定、可复算；应用层保留人的判断，不把未确认规则硬编码成事实。失败处理也要写进方案：字段缺失显示“未知”不默认 0；规则冲突并列显示；口径未确认只提示、不阻断，并写清谁确认。每加一个派生指标，都要能回答它支撑哪条 FR 的哪个判断；答不上来就是装饰。

界面意图：先写要完成什么，再选控件

到了界面，很多人直接拖组件。更稳的顺序是先写 Interface Expectation（界面意图）：用户来这里要完成什么意图，需要看到哪些信息，做哪些交互，失败时怎么办。工具和控件最后再选。

S1 只需四个区域就能走完一次决策（数字为【示例】）：

界面区域 用户意图 必须看到 关键交互 失败处理
额度全景 判断从哪里开始调整 3 个演示亚专科（真实科室共 12 个，作为背景）的需求、额度、已分配、剩余、缺口 切换月份、按缺口排序 数据缺失显示未知，不显示 0
分配台 决定谁分到哪个亚专科、多少人天 人员池、可用天数、资质、当前分配 拖入、填人天、保存 超可用天数时阻止并说明差额
冲突面板 决定先解决哪个冲突 冲突类型、涉及对象、差额、建议动作 定位到对应分配、跳转调整 规则冲突时并列显示，不替用户选
审批页 判断能否发布 冲突是否清零、总额度是否超限 批准、退回并写意见 不满足条件时禁用批准并说明原因

检验界面意图，看每个区域连起来能否从“看到缺口”一路走到“审批写回”，中间不离开系统、不打电话问人。走不通，缺的不是页面，是对象、状态或增强。反过来，界面也能校验模型：需要的信息找不到对象，说明模型漏了；对象在界面上完全没有入口，可能是多余的。

四件套怎么串起来

四件套互相校验，分工是：

产物 回答的问题
A04-01 决策清单模板 有哪些决策，谁在何时、依据什么、做什么动作？
A04-03 对象模型模板 世界由哪些对象组成，关系和基数是什么？
A04-04 生命周期与写回模板 对象有哪些状态，哪个 Action 写回哪些字段？
A04-05 增强与界面模板 缺什么信息、放哪层、界面怎么支撑意图？

串接顺序是：先从一页纸和 FR 生成决策清单（A04-01），再把决策涉及的名词收成对象（A04-03），然后给会变的对象画状态机与写回（A04-04），最后补增强和界面意图（A04-05）。

检查四条：每条 FR 能否找到对象和动作？每个会变的状态是否有 Action、写回字段和权限？每个增强能否指到一条 FR 的判断？每个界面意图能否走通端到端决策？

四条都过，方案才算支撑决策；断一条，就回决策清单重对齐，不要用更多页面去补。

建造顺序：先有决策，再扩空间，最后让模型反馈

四件套画完，还要决定先建哪一块。顺序只有一条：先把一个决策跑通，再扩大，最后才让模型插手。【官方】[S04]

  1. 数据资产 + 引导式决策：数据能进来，对象建得对，陈静能完成一次真实分配并写回。不求覆盖全部场景，只求一条完整链路。
  2. 扩决策空间：同一条链路接更多对象、角色和 Action，例如把组长确认、临时调整纳入同一条生命周期。
  3. 模型反馈：有了稳定的决策记录，才谈预测、推荐、异常检测。模型吃的是前两步留下的结构化数据。

反过来做，先上模型、先做大屏，会把没验证过的假设固化：界面热闹，决策一次都没跑通，写回也没有落点。三个常见建模问题——组织单位对应什么、资格信息从哪来、几套时间口径怎么对齐——都该在第 1 步之前问清。

G4 方案设计门的可观察标准：每条 FR 可验收；对象模型区分 core、derived、use case；生命周期有 Action 与写回；增强标明数据层或应用层；人机控制矩阵（每一步由谁判断、谁验证、怎么回滚，工作台详述）每步都有级别与责任人；MVP 范围明确。画不出状态迁移，不是“文档还没写完”，而是决策还没有落成数据。

动手 25 分钟：为你的切片补齐四件套。

  1. 04-01_决策清单.md：最终决策拆成 3–6 行，写决策人、时点、输入、动作、频率、影响对象。
  2. 04-03_对象模型.md：列 5–9 个对象，标类型，写属性、关系、基数、来源、负责人。
  3. 04-04_生命周期与写回.md：挑一个会变的对象，画状态链，填 Action、迁移后状态、写回字段、权限、校验。
  4. 04-05_增强与界面.md：列 3–6 个增强并标层级；写 3 个界面区域，每个写意图、信息、交互、失败处理。

三条自检：

  • 对象模型里有没有把“表”当“对象”（出现“临时表”“中间表”就要改）？
  • 是否有 Action 明确写了写回字段，且关掉重开能看到？
  • 每个增强是否写清了字段缺失和规则冲突时的处理？

参考答案（分配对象）：

Allocation，use case；属性为月份、人员、亚专科、人天、状态；连接人员与亚专科；来源是用户在分配台创建，负责人陈静。状态链：建议 → 已确认 → 已发布 → 调整中 → 已归档。“发布”写回状态与发布时间，同时更新额度已用与剩余；只有周主任可发布，发布前校验冲突清零、总额度未超限。

常见坑

坑 1：把对象模型画成 ER 图（实体-关系图，只描述表和关系，不描述动作与状态）。 表现：一上来就是主键、外键、中间表。后果：业务关系被存储细节淹没，“分配”“冲突”找不到对应物。 处理：先用业务名词列对象、关系、基数、来源；存储设计放到实现阶段。

坑 2：只画页面，不画状态。 表现：原型很完整，但问“确认后变成什么状态”答不上来。后果：演示只能点，不能往下走。 处理：每个会变的对象补状态链，每个 Action 写清迁移后状态和写回字段。

坑 3：把写回留到“后面再接”。 表现：先做只读演示，写回等权限下来再说。后果：审批链断在最后一步。 处理：写回是方案的一部分；权限没下来就先写本地对象，并标明真实写回的风险。

坑 4：增强放错层。 表现：冲突计算靠手工勾选，或建议动作硬编码成唯一答案。后果：要么易漏，要么把人的判断伪装成系统事实。 处理：能算的放数据层，要判断的放应用层；未确认口径只提示、不阻断。

三问自测

1. 对象模型和数据库表的区别是什么？ 对象模型描述业务对象、关系、基数和动作；数据库表描述数据怎么存。一个对象可能对应多张表，派生对象可能没有表。先有对象模型，再决定存储。
2. 为什么说“写回是方案的一部分”，而不是开发细节？ 写回决定决策是否真的落成数据。没有写回，审批只是界面动作，流程无法继续。方案阶段要写清哪个 Action 改哪些字段、谁有权限、失败怎么回退。
3. 一个增强应该放数据层还是应用层？ 看是否依赖用户手工修改、能否由数据确定。能稳定复算的（剩余额度、缺口、超排）放数据层；需要人判断或临场决定的（建议动作、未确认口径）放应用层。

本章带走

  1. 方案设计按顺序回答四件事：对象模型、生命周期与写回、数据增强、界面意图；先对象后页面。
  2. 对象模型不是数据库表；它区分 core、derived、use case，并描述关系、基数和动作。
  3. 写回是方案的一部分：没有状态迁移和字段变化，决策就还停留在幻灯片上。

本页术语

Object Model（对象模型） Object Model

用对象、关系和基数描述业务语义的草图，区分 core、derived、use case 三类对象。

Lifecycle Diagram（生命周期图） Lifecycle Diagram

描述对象有哪些状态、哪些 Action 推动状态迁移的图；画不出状态机，说明决策还没有落成数据。

Enrichment（数据增强） Enrichment

为了支撑决策输入而补充的对象级或属性级派生概念；不依赖用户手工修改的增强应放在数据层。

Interface Expectation（界面意图） Interface Expectation

先写用户要完成什么意图、需要怎样的交互，再决定用什么工具实现。

Ontology（本体） Ontology

把业务对象、关系和可执行动作显式建模出来的语义层，相当于这个 use case 的 API。

写回 Write-back

用户在界面上的动作真正修改了对象数据，而不只是切换页面；没有写回，决策就没有落成数据。

状态机 State Machine

描述对象状态与 Action 迁移关系的图；和泳道图视角不同，不要混用。

Solution Design（方案设计） Solution Design

把功能需求拆成对象模型、生命周期、数据增强和界面意图四件产物的过程。

Core 对象 Core Object

直接映射源系统一个数据粒度的对象，例如人员、班次。

Derived 对象 Derived Object

源系统没有、需要计算或人工维护出来的概念，例如资质、缺口。

Use Case 对象 Use Case Object

用户在业务流程中会主动创建、修改的对象，例如配额方案、调整记录。

记录系统 System of Record

组织保存权威业务数据与审计记录的核心系统；写回必须尊重它的权威，而不是另造一套账本。
