一页纸对齐范围

用六段式 one-pager 把切片压成一页，写解决什么、不解决什么、怎么算成功。

本页要回答怎样让业务方在半小时内对“做什么、不做什么”达成一致？

读完你能

  • 说出一页纸六段各自的作用；
  • 把决策清单压成一条最终决策；
  • 写出一页可评审的 one-pager。

前置

先读：看清今天实际怎么运转

周三下午，你把业务方、组长和信息科拉进同一间会议室。开场大家都同意：“先做个排班系统。”

两小时后，白板上出现了三张不同的图：业务方想“月底分额度别再来回改”，组长想“我们组缺的人要能被看见”，信息科想“先把三个 Excel 对成一个版本”。每个人都点头，理解却不一样。

再写三十页需求文档，只会让分歧藏得更深。你需要一页纸：在半小时内，让所有人对“谁做什么决定、凭什么、做完什么算成功、这次不碰什么”说出同一句话。

一页纸不是缩小版需求文档

One-pager（一页纸） 把范围、决策、相关方、成功标准和现状压在一页内。它的价值不在“短”，而在迫使范围收敛：一页写不下，通常不是字太少，而是还没决定这次到底做哪一件事。

两者分工不同：

一页纸 正式需求文档
主要读者 业务方、审批人、实施团队 开发、测试、验收
主要作用 对齐“做什么、不做什么” 固定“怎么做、做到什么程度”
详细程度 一段一句话，能当场争论 字段、规则、异常、接口

一页纸不是合同替代品，而是合同的前置共识：业务方点头，后面才值得展开细节。

停一下：如果现在让你把项目压成一页，你会先写“功能”，还是先写“谁在什么时候做什么决定”？

先写功能，往往得到功能清单；先写决策，才有机会得到可验证的端到端链路。

六段：每一段只回答一个问题

一页纸的正文由六段组成，顺序不要调换：先有人，才有决定；先有决定，才谈输入和动作；最后才是价值和边界。六段分别回答：用户（谁做决定）、决策（哪一个决定）、输入（凭什么）、动作（决定后做什么）、价值（什么变化）、不做什么（边界在哪）。

用户：写角色，不写部门

用户不是“病理科”，而是“陈静主操作；周主任审批；赵岚等组长提需求并确认”。三个人做三件不同的事，不能合并成一个“业务方”。

分清四种角色：操作者（点界面的人）、审批者（能说“重做”的人）、被影响者（工作会变的人）、数据/权限把关人（决定能否取数、写回的人）。一页纸重点写前两种，后两种放“相关方”；出现“各部门配合”，基本等于没写。

相关方不能只列名字，还要写清“他关心什么、可能在哪个点上反对”。CB-00 的四个人可以当一张最小冲突表：

角色 在意什么 可能的反对/分歧
周主任（审批） 总额度不超、临床不出事、别天天救火 方案会增加他的审批动作，或让他承担系统判断错误
陈静（操作） 少返工、别靠回忆、月底不被追问 新流程比 Excel 更慢，或出了问题仍要她手工兜底
赵岚（需求提出） 本组缺口被看见、人手够用 额度按“总量平均”分，而不是按结构性缺口分
孙老师（额度发放） 口径统一、可审计 现场改口径，导致月底对不上账
刘工（数据权限） 不增加系统负担、权限可控 写回范围过大，或权限绕过既有审批

这张表不是让一页纸变长，而是提前暴露“谁会说不”。如果某一行写不出反对理由，通常说明你还没和这个人说过话。

决策：一条最终决策

决策段只写一个最终决定。推荐句式：

____（角色）在____（时点），根据____（输入），决定____（决定），并触发____（动作）。

以 案例 CB-04 为例：陈静在每月 25 日前，根据各亚专科需求、外部额度和人员可用天数，决定本月每个亚专科用多少额度、分给谁，并写回分配记录、提交确认。

需要用“并且”连接两个互不相干的决定时，通常说明这是两个切片，拆开。

输入：决定前必须看到的信息

输入不是数据清单，而是这个决定离不开的信息。每写一条问：缺了它，决定会不会变？不会变的删掉。

CB-04 列了五类输入：月度需求、下发额度、人员可用天数、人员资质与可上班型、上月结转与借用规则。每一条都要说清来源、口径和新鲜度：例如“可用天数”是否已扣年假、门诊、外出会诊，否则同一个词两个人算出两个数。

输入可以不完美，但必须标状态：已有、待补、待确认；不要把“待确认”写成“已有”。

动作：决定之后发生什么

动作要能被看见。CB-04 写：在“亚专科 × 人员”界面调整；系统即时显示已分配、剩余额度、缺口与冲突；保存后写回；提交组长确认、主任审批。

这里有两类动作，不能混：系统动作（计算、提示、保存、写回）和人的动作（确认、调整、审批、拒绝）。

只有“查看报表”、没有写回或确认，它更接近看板；五天验证时，你很难证明“决策变了”。

价值：可观察的变化

价值段要回答：现在多少，做完变成多少，怎么测——即 KPI（关键绩效指标） 的定义、基线、目标、测量方式。

CB-04 写：分配耗时从约 3 小时降到 1 小时以内【示例】；冲突在排班前暴露，而非月中才发现；额度、分配、调整有同一份可追溯记录。

注意“约”字：基线来自回忆时必须写“约”，并注明待现场复测。没有基线的价值不是价值，是愿望。

不做什么：给范围装围栏

“不做什么”至少三条，每条带理由或归属。CB-04 排除：个人排班（S2）、住院总轮转（S3）、工资绩效核算，以及“自动替人做最终决定”。

这条清单让“做什么”可信：业务方看到 S2 被排除，反而更相信 S1 能在五天内交付；有人加需求时，你也能回答“这条属于 S2，下一轮再谈”。

停一下：六段里，哪一段最容易被写成“正确的废话”？

通常是“价值”和“不做什么”。判断标准很直接：五天后，你能不能指着一条记录说“变了”或“没变”？如果不能，这一段还需要重写。

决策清单：把“决策”压成一条

决策清单 是一行一个决策的表：决策、决策人、时点、输入、动作、频率。这里先要一张决策清单 v0：从 A03-02 的角色-决策行里挑出与这一片有关的，用来决定一页纸承诺哪一条。正式的 A04-01 在方案设计阶段再展开，补上中间决策和影响对象；权限不在决策清单里，落在 A04-04 生命周期的“谁可操作”。

案例 CB-03 有四行：

编号 决策 类型 是否进这次 one-pager
DC-1 各亚专科本月额度怎么分 最终决策的一部分 进
DC-2 某个人分到哪个亚专科 最终决策的一部分 进
DC-3 出现缺口时怎么办 中间决策 不进五天 Demo
DC-4 最终方案是否发布 审批动作 只做最小确认

编号用 DC（Decision），避免和 Day1 工具包的 D1（第一天）混淆。

压缩规则：DC-1、DC-2 合并成一条“额度分配方案”的确认；DC-3 是需要例外规则的中间决策；DC-4 是审批动作。一页纸只承诺 DC-1/DC-2，不把 DC-3 的借调、改派、申请额外额度放进五天。到了 A04-01，DC-3 会以“出现缺口时怎么办”保留为中间决策行，DC-4 写成审批动作，赵岚的组长确认作为 DC-4 之前的子步骤，不单独占一行。

DC-3 一旦进入范围，就要定义缺口口径、向谁借、跨月怎么还、谁有权批，五天验证不了。把它留在边界外，S1 才能端到端跑通。

为什么本教程先讲现状，再写一页纸

官方 use case lifecycle 的公开顺序，是先描述 use case、提炼功能需求，再做解决方案设计和开发排序 [S01]。也就是说，官方材料默认你已经知道“用户是谁、要改变什么决定”。

本教程把顺序调成了：

观察现状（As-is）→ 列决策清单 → 选切片 → 写 one-pager → 再写功能需求与方案

原因很实际：零基础的读者如果一进场就写一页纸，很容易把会议上的想象写成“用户”和“决策”。先看陈静怎么收额度、怎么翻纸质本、怎么打电话协调，你才知道“决策”到底发生在哪一步，输入到底缺在哪。

两种顺序产物形态不同，但核心问题一致：谁的什么决定，凭什么，值不值得继续。 官方顺序不是错误；本教程的顺序是面向零基础现场观察的教学改编【实践】。你也可以先按官方材料框出 use case，再回现场用 As-is 校验，只要别把“会议共识”当成“现状证据”。

用 CB-04 走一遍六段

把 CB-04 拆开看，六段各自承担什么：

段落 CB-04 的关键内容 这一段做对了什么
用户 陈静主操作；赵岚提需求并确认；周主任审批 操作者、提出者、审批者分开
决策 每个亚专科用多少额度、分给谁 只有一个最终决定
输入 需求、额度、可用天数、资质、结转规则 每条都能对应到决定
动作 调整、即时提示、写回、提交确认 有系统动作，也有人的动作
价值 3 小时降到 1 小时以内【示例】；冲突提前暴露 有基线、有可观察变化
不做什么 不做 S2、S3、工资绩效、自动最终决定 边界具体，能挡住现场加需求

页脚三块也别省：成功标准是五天验收条件，不是长期 KPI；相关方写清审批、操作、需求、额度口径、数据权限；现状一句话说清“Excel + 微信 + 记忆 + 纸质草表”。

可抄模板：A03-05

A03-05 use-case one-pager模板 的空白模板如下。先把标题和六段填满，再补成功标准、相关方和现状；不要反过来先写功能。

A03-05 use-case one-pager 可直接复制
# <切片名> one-pager
1. 用户：<操作者>；<审批者>；<需求提出/确认者>
2. 决策：<角色>在<时点>，根据<关键输入>，决定<一个决定>。
3. 输入：<输入 1>（来源/口径/状态）；<输入 2>（……）
4. 动作：<系统动作：计算/提示/写回>；<人的动作：确认/审批>
5. 价值：<基线> → <目标>；测法：____；数据来源：____
6. 不做什么：<范围 A，理由>；<范围 B，理由>；<范围 C，理由>

成功标准（五天验证）：<可观察条件 1>；<可观察条件 2>
相关方：<审批>、<操作>、<需求>、<数据/权限>
现状：<今天实际怎么做，一句话>

模板自带的三个硬检查：决策段只能有一个“决定”；“不做什么”至少三条；价值段要么有基线，要么写“待校准”，并同时写清测量方式、数据来源、校准日期和负责人——四项缺一项，不算通过。

动手 12 分钟：用你手上的项目，写出第一版 A03-05。

  1. 打开 03_现状与切片/03-05_use-case-one-pager.md，从 A03-02 里选一行最终决策，套进决策句。
  2. 补六段。输入标注来源和状态；“不做什么”至少三条，每条对应一个候选切片或明确边界。
  3. 价值写“基线 → 目标 → 测法”；没有基线就写“约”并标“待校准”，同时写明测量方式、数据来源、校准日期和负责人。

三条自检：

  • 用户是否是具体角色，且操作者与审批者分开？
  • 决策段是否只有一个“决定”，没有塞进功能清单？
  • 每条“不做什么”是否有理由，能在现场直接引用？

参考答案（CB-04 的压缩句）：陈静在每月 25 日前，根据需求、额度和可用天数，决定每个亚专科用多少额度、分给谁，写回并提交确认；S2、S3、工资绩效不在本次范围。

坑 1：把一页纸写成功能清单。 表现：决策段出现“支持导入、导出、提醒、审批、统计”。后果：范围无法收敛，五天做不完。 处理：回到决策清单，只保留一条最终决策；其他功能标为“动作”或“不做什么”。

坑 2：用户写成部门或“所有人”。 表现：“用户：病理科”。后果：不知道谁操作、谁审批，界面和验收都没有对象。 处理：写具体角色，并区分操作者、审批者、被影响者、数据把关人。

坑 3：价值没有基线。 表现：“提升效率、降低出错”。后果：五天后无法判断有没有变好。 处理：写“当前约多少 → 目标多少 → 怎么测”；拿不到数就写“待校准”，不要编。

坑 4：“不做什么”空着。 表现：六段只填了五段，或写“其他需求后续再说”。后果：现场每加一个需求，范围就膨胀一次。 处理：至少三条，每条带理由或归属切片；加需求时先问“它属于哪条边界”。

三问自测

1. 六段中，哪一段最能防止范围膨胀？为什么？ “不做什么”。它把边界写成可引用的句子，现场加需求时可以直接说“这条属于 S2，下一轮再谈”。没有它，通常也说不清“做完什么算成功”。
2. 官方 lifecycle 与本教程的顺序差在哪？这说明官方错了吗？ 官方公开顺序是先描述 use case、提炼功能需求，再做方案设计和开发排序；本教程先观察现状、列决策清单，再写 one-pager。差别来自读者起点：零基础读者需要先用 As-is 校验会议想象。官方不是错误，本教程是有意的教学改编【实践】。
3. CB-03 的 DC-3 为什么不进这次 one-pager？ DC-3 是“出现缺口时怎么办”的中间决策，涉及借调、改派、申请额外额度等例外规则；要定义缺口口径、借用权限和跨月归还，五天验证不了。一页纸只承诺 DC-1/DC-2。

本章带走

  1. 一页纸不是缩小版需求文档，而是让业务方在半小时内对“做什么、不做什么”达成一致的范围围栏。
  2. 六段各回答一个问题：用户、决策、输入、动作、价值、不做什么；决策只能有一条，价值必须有基线，边界至少三条。
  3. 本教程先看现状再写一页纸，是对官方 lifecycle 的教学改编；决策清单负责详细，一页纸负责收敛，两者不能互相替代。

本页术语

Functional Requirement（功能需求） Functional Requirement

用“谁、在什么界面、依据什么输入、做什么决定、产生什么动作”写成的可验收句子。

首次解释

KPI（关键绩效指标） Key Performance Indicator

能用一个数字衡量“有没有变好”的指标，必须有定义、基线、目标和测量方式。

首次解释

One-pager（一页纸） Use Case One-pager

把范围、决策、相关方、功能需求、指标和现状压在一页内的对齐工具，不是正式需求文档。

决策清单 Decision List

把最终决策、中间决策、决策人、时点、输入和动作逐条列出的表；一个决策一行。
